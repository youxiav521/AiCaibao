# 单文件合规检查代码流程说明

## 1. 口径说明（重要）

`single_file_policy_checks` 的“单文件”是输出粒度，不是执行输入粒度。

- 输入是资源库级：`files[] + frameworks[]`
- 执行时在资源库范围做相关性评估、证据检索、规则执行
- 输出时再按文件拆分回传 `audited/completed`

一句话：仓级审查，文件级回传。

## 2. 总体流程（Hybrid）

核心入口：`single_file_policy_check_service.py`

1. 请求标准化：`files[] -> ResourceFile[]`
2. 构建仓级上下文：`repository + material_store + MaterialRetriever`
3. 并发构建文档画像 `document_profiles`
4. 按 `framework/requirement` 并发执行 `_review_requirement_hybrid`
5. requirement 结果汇总到每个文件
6. 计算文件级 `overall_status/statistics/summary`
7. 返回 `SingleFilePolicyCheckResult[]`

`metadata.executionMode` 为 `hybrid_repository_per_requirement`。

## 3. 政策-文件匹配的详细步骤（重点）

### 3.1 文档初分类与画像（含 shared）

位置：`policy_relevance_profiles.py`

文档画像构建会调用 shared 组件：

- `..shared.doc_profile.classify_doc_profile_with_llm_fallback`
- `map_doc_types_to_policy_doc_types`
- `collect_policy_doc_type_anchor_terms`

然后补充本模块特征：

- `domain_tags`（领域标签）
- `anchor_terms`（锚点词）
- `field_terms`（字段词）
- `is_business_overview`
- `evidence_density`
- `document_signal_count`

### 3.2 requirement/control 规则画像

同文件中会构建：

- `RequirementProfile`：目标文档类型、领域、意图、是否 `collection_heavy`、锚点、字段、置信度
- `ControlProfile`：目标文档类型、领域、检查模式 `check_mode`、目标字段/实体、证据期望、严格度、置信度

### 3.3 控制项相关性打分（match 核心）

位置：`policy_relevance_matcher.py`

特征项：

- `doc_type_compatibility`
- `domain_overlap`
- `anchor_overlap`
- `field_overlap`
- `entity_overlap`
- `evidence_feasibility`
- `retrieval_strength`
- `overview_penalty`

总分（0-1）：

`0.24*doc_type + 0.14*domain + 0.14*anchor + 0.12*field + 0.08*entity + 0.14*evidence + 0.2*retrieval - 0.14*overview_penalty`

决策阶段：

- `hard_skip`：高置信类型不匹配且无有效语义/检索信号
- `soft_skip`：分数低于软阈值（默认 0.30）
- `review`：进入审查候选
- `fast_fail_candidate`：偏“材料存在性”且证据/检索都弱的候选

灰区阈值默认：

- soft skip 阈值：`0.30`
- review 阈值：`0.55`

### 3.4 执行门控（不是 review 就一定执行）

位置：`policy_check_relevance.py`

`_apply_execution_gate` 会把 `review` 再分流为：

- `review_execute`：允许进入正式执行
- `review_hold`：暂不执行，仅保留相关性结论

门控依据包括：

- `retrieval_strength`
- 锚点/字段/实体/领域重叠
- `fact_hit_count`
- 业务概览文档的惩罚条件

之后还会 `prune_controls_for_execution`，限制每个 requirement 真正执行的控制项规模，优先保留高分高信号项。

### 3.5 requirement 执行与全库结论

位置：`single_file_policy_check_service.py` + `policy_check_execution.py`

- 先按 control 聚合候选文件，得到 `control_candidate_files`
- 每个 requirement 只执行“筛过且允许执行”的 relevant controls
- 执行对象是整个 repository（不是单文件）
- 失败抑制：低相关/低检索强度的 `fail` 结果可降为 `uncertain`
- fast-fail 路径：某些条件下可直接给 `fail/uncertain`

### 3.6 投影回单文件（单文件结果如何来）

位置：`policy_check_projection.py`

对每个已执行 control：

1. 先挑候选文件（受预算和 `candidate_file_score_margin` 控制）
2. 将全局 control 结果投影到具体 file
3. 若该文件没有直接 evidence，尝试从 retrieval 命中推断 `infer_file_evidence_from_retrieval`
4. 必要时降级结果（如全局 `pass/fail` 在文件侧转 `skipped/uncertain`）

因此单文件结果是“全库审查结果 + 文件归因信号”的投影结果，不是文件独立重跑一遍。

## 4. 并发模型

- 文档画像并发：按文件并发构建
- requirement 审查并发：`framework x requirement` 并发
- 每个 requirement 内：按 `control x file` 评估相关性
- 正式执行并发：受 `maxConcurrency` 的 `asyncio.Semaphore` 限流（默认 12）

## 5. 回调与输出

`router.py` 将内部结果转换为 Java 侧约定格式：

- `started`
- `audited`
- `completed`
- `error`（单文件失败时）

`completed` 包含文件级统计（requirements/controls/pass/fail/uncertain/skipped/passRate/durationSeconds）。

## 6. 关键配置默认值

见 `policy_check_config.py`：

- `model_id = model_bailian_policy_check`
- `max_concurrency = 12`
- `relevance_threshold = 4.5`
- `execution_retrieval_floor = 0.22`
- `fail_relevance_floor = 0.58`
- `fail_retrieval_floor = 0.2`
- `candidate_file_score_margin = 0.06`

## 7. 本地测试脚本

`single_file_policy_local_test.py` 支持：

- 直接读取完整请求 JSON（含 `files/frameworks`）
- 读取 `resource_repository` 结构并补 `frameworks`
- 目录输入时可自动聚合 MinerU JSON 为仓级输入
- 在脚本顶部改 `DEFAULT_*` 即可演示，无需现场敲复杂命令
- 落盘完整模型输出并打印回调结果
