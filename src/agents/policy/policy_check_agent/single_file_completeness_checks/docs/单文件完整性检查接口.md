# 单文件完整性检查接口

## 1. 概述

该接口用于对单个文档执行完整性检查，判断文档是否缺失银行要求的必备章节或必备要素。

- 能力目录：`single_file_completeness_checks`
- 提交接口：`POST /api/policy/single-file/completeness/jobs`
- 默认回调接口：`POST /result/completeness/callback`
- `category` 固定返回：`COMPLETENESS`
- 执行方式：异步任务
- 回调事件：`started`、`audited`、`completed`、`error`

## 2. 当前检查口径

当前实现不是只检查“是否单独成章”，而是同时支持两种满足方式：

- `section`
  - 文档中存在独立章节或明确标题
- `element`
  - 文档未单独成章，但正文已经覆盖了对应要素

结果会通过 `attributes.satisfactionMode` 返回：

- `section`
- `element`
- `missing`

## 3. 必查项确定逻辑

优先级如下：

1. 如果请求传了 `requiredSections`，直接按显式章节检查
2. 如果请求传了 `documentType`，按内置 profile 检查
3. 如果未传 `documentType`，先用 LLM 在固定 profile 集合中分类
4. 如果分类不稳定或返回 `unknown`，再用 LLM 选择 section groups
5. 如果仍不稳定，回退到最小通用集：
   - `目的`
   - `适用范围`

## 4. 请求字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `checkReportId` | 是 | Java 侧任务主键 |
| `fileId` | 否 | 文件 ID，不传时默认使用 `checkReportId` |
| `fileName` | 否 | 文件名 |
| `callbackUrl` | 否 | 回调地址，不传时使用 `POLICY_CALLBACK_BASE_URL + /result/completeness/callback` |
| `docContent` | 是 | MinerU 解析后的文档 JSON 数组 |
| `documentType` | 否 | 文档类型 profile |
| `requiredSections` | 否 | 显式指定必查章节，优先级最高 |
| `modelId` | 否 | LLM 模型 ID，默认 `model_bailian_policy_check` |
| `enableLlm` | 否 | 是否启用 LLM，默认 `true` |
| `llmRetryAttempts` | 否 | LLM 重试次数，默认 `2` |

## 10. 关键字段说明

### 10.1 `fileStatus`

- `P`
  - 处理中
- `S`
  - 审核完成且无 fail
- `F`
  - 审核完成且存在 fail

### 10.2 `controlResult.status`

- `pass`
- `fail`
- `uncertain`

### 10.3 `controlResult.level`

- `NONE`
- `MEDIUM`
- `HIGH`

### 10.4 `attributes`

常用字段：

- `matchedBy`
  - `title`
  - `content`
  - `missing`
  - `llm_semantic`
  - `llm_uncertain`
- `satisfactionMode`
  - `section`
  - `element`
  - `missing`
- `isStandaloneSection`
  - `true`
  - `false`
- `allowElementOnly`
  - 当前检查项是否允许“正文提到即可算满足”
- `matchedSectionName`
  - LLM 语义补判时识别到的等价章节名
- `confidence`
  - LLM 补判置信度

## 11. 当前边界

- 当前更适合制度、办法、指引、合同、尽调报告等结构化文档
- 当前只做单文件内部检查，不做跨附件补全判断
- 当前已支持“未单独成章，但正文已覆盖要素”的判断
- section 级 LLM 只用于补规则漏判，不直接自由生成检查配置
- 当 LLM 无法稳定判断时，结果会落为 `uncertain`
