# Policy Check Agent Java 对接说明

## 1. 接口职责


1. Java 调我们的发起接口
   - `POST /api/policy/check`
2. 我们回调 Java 的结果接口
   - `POST /api/policy/check/result/modelcallback`

注意：
- `/api/policy/check/result/modelcallback` 是给我们回调结果用的。
- `/api/policy/check/result/sse` 是 Java 自己给前端做 SSE 订阅用的，我们不会调用这个地址。

## 2. 调用流程

1. Java 调 `POST /api/policy/check` 发起任务。
2. 我们立即返回接收成功。
3. 后台异步执行合规检查。
4. 我们通过 `POST /api/policy/check/result/modelcallback` 持续回调结果给 Java。
5. Java 再把结果写入自己的 `GET /api/policy/check/result/sse` SSE 通道，供前端订阅。

## 3. 发起接口

- Method: `POST`
- Path: `/api/policy/check`

### 3.1 请求体

顶层建议使用 camelCase，后端同时兼容 camelCase 和 snake_case：

```json
{
  "resourceRepository": {
    "id": "base_123456",
    "title": "SOC 2 合规资源库",
    "description": "SOC 2 合规资源库，包含合规要求、控制项、测试用例等",
    "files": [
      {
        "fileId": "file_123456",
        "fileName": "资料文件.pdf",
        "content": []
      }
    ]
  },
  "frameworks": [
    {
      "frameworkId": "fw_2024",
      "fileId": "file_123456",
      "name": "对应文件名",
      "description": "生成的文件描述信息",
      "requirements": [
        {
          "requirementId": "req_001",
          "title": "识别到的需求标题文本",
          "description": "生成的需求描述文本",
          "sourceText": "原始文本内容",
          "sourceLocation": {
            "fileId": "file_123456",
            "elementIds": [12, 13, 14]
          },
          "status": "approved",
          "controls": [
            {
              "controlId": "ctrl_001",
              "controlType": "生成用来描述控制项的类型",
              "risk": "high",
              "logicDescription": "生成用来描述控制项的逻辑描述",
              "sourceText": "原始文本内容",
              "sourceLocation": {
                "fileId": "file_123456",
                "elementIds": [12, 13, 14]
              }
            }
          ]
        }
      ]
    }
  ],
  "modelId": "model_bailian_policy_check",
  "maxConcurrency": 8,
  "checkReportId": "rpt_xxx",
  "callbackUrl": "http://java-host/api/policy/check/result/modelcallback"
}
```

说明：
- `resourceRepository.files[].content` 传 MinerU 解析后的内容。
- `frameworks[].requirements[].controls[]` 按当前政策抽取 JSON 原样传入。
- `checkReportId` 可选；不传时后端自动生成。
- `callbackUrl` 可选；不传时按以下顺序回调：
  - `POLICY_CALLBACK_BASE_URL + /api/policy/check/result/modelcallback`
  - `CONTENT_GENERATE_CALLBACK_URL + /api/policy/check/result/modelcallback`
  - 默认基础地址 `http://10.192.72.11:32223`

### 3.1.1 请求字段说明

`frameworks[].requirements[].controls[]` 字段：

## 4. Java 回调接口

- Method: `POST`
- Path: `/api/policy/check/result/modelcallback`

我们回调 Java 时，最外层固定是下面这个结构：

```json
{
  "frameworkId": "fw_2024",
  "fileId": "file_123456",
  "event": "start | message | complete | error",
  "data": "{...json字符串...}"
}
```

说明：
- 最外层只有 4 个字段：`frameworkId`、`fileId`、`event`、`data`。
- `data` 是 JSON 字符串，Java 侧需要再反序列化一次。
- 业务字段不在最外层，全部在 `data` 里。
- 当前不会再单独回调 `control_result` 这种最外层事件。

### 4.1 最外层回调字段说明

| 字段 | 必有 | 类型 | 含义 | 取值/规则 |
| --- | --- | --- | --- | --- |
| `frameworkId` | 是 | string | 当前 framework id | 来自请求中的 `frameworks[0].frameworkId` |
| `fileId` | 是 | string | 当前文件 id | 优先取 `frameworks[0].fileId`，取不到时回退 `resourceRepository.id` |
| `event` | 是 | string | 回调事件类型 | `start` / `message` / `complete` / `error` |
| `data` | 是 | string | 业务数据 JSON 字符串 | Java 侧需再次反序列化 |

## 5. 回调事件说明

### 5.1 start

```json
{
  "frameworkId": "fw_2024",
  "fileId": "file_123456",
  "event": "start",
  "data": "{\"checkReportId\":\"rpt_xxx\"}"
}
```

`start.data` 字段说明：

| 字段 | 必有 | 类型 | 含义 | 取值/规则 |
| --- | --- | --- | --- | --- |
| `checkReportId` | 是 | string | 本次检查任务标识 | 来自请求或后端自动生成 |

### 5.2 message

每完成一个 requirement，就回调一次 `event=message`。

`message` 的 `data` 反序列化后结构如下：

```json
{
  "checkReportId": "rpt_xxx",
  "status": "running",
  "summary": {
    "totalRequirements": 10,
    "totalControls": 45,
    "passed": 8,
    "failed": 1,
    "uncertain": 2,
    "skipped": 0,
    "description": "Current stage summary",
    "durationSeconds": 12.5,
    "passRate": "72.7%"
  },
  "requirement": {
    "requirement_id": "req_001",
    "requirement_title": "识别到的需求标题文本",
    "framework_id": "fw_2024",
    "status": "completed",
    "progress": "1/10",
    "elapsed_seconds": 12.5,
    "check_results": {
      "requirementId": "req_001",
      "result": "fail",
      "reason": "整体结论",
      "evidence": [],
      "controlResults": []
    },
    "control_results": [
      {
        "requirementId": "req_001",
        "controlId": "ctrl_001",
        "result": "fail",
        "reason": "未找到对应材料",
        "degraded": false,
        "evidence": [
          {
            "evidenceId": "evidence_xxx",
            "fileId": "file_123456",
            "elementIds": [12],
            "summary": "摘要信息",
            "quotedText": "前端展示用的原文片段"
          }
        ]
      }
    ]
  }
}
```

### 5.3 message 字段层级说明

`message.data` 里分三层：

1. 第一层：本次回调整体信息
   - `checkReportId`
   - `status`
   - `summary`
   - `requirement`

2. 第二层：`requirement`
   - 表示当前完成的 requirement
   - requirement 级结论在 `requirement.check_results`

3. 第三层：`requirement.control_results[]`
   - 表示当前 requirement 下每个 control 的检查结果
   - control 级结论在 `requirement.control_results[].result`
   - control 级原因在 `requirement.control_results[].reason`
   - control 级降级标记在 `requirement.control_results[].degraded`

重点：
- `requirement.check_results.result` / `reason` 是 requirement 层结论。
- `requirement.control_results[].result` / `reason` 是 control 层结论。
- `requirement.control_results[].degraded` 表示该 control 是否走了自动降级/兜底。
- `control_results[]` 不是最外层回调事件，而是 `message.data.requirement` 下面的数组。
- 当前不再单独发送最外层 `control_result` 事件。
- `docFolderId` 取自发起请求里的 `resourceRepository.id`，在 `complete` 和 `error` 回调中原样返回。

### 5.3.2 `message.data` 字段说明

第一层字段：

| 字段 | 必有 | 类型 | 含义 | 取值/规则 |
| --- | --- | --- | --- | --- |
| `checkReportId` | 是 | string | 本次检查任务标识 | 与 `start`/`complete` 中保持一致 |
| `status` | 是 | string | 任务当前状态 | 当前固定为 `running` |
| `summary` | 是 | object | 当前累计汇总 | 见下方 `summary` 字段说明 |
| `requirement` | 是 | object | 当前刚完成的 requirement 结果 | 见下方 `requirement` 字段说明 |

`message.data.summary` 字段：

| 字段 | 必有 | 类型 | 含义 | 取值/规则 |
| --- | --- | --- | --- | --- |
| `totalRequirements` | 是 | integer | 总 requirement 数 | `frameworks[].requirements` 总数 |
| `totalControls` | 是 | integer | 当前已统计到的 control 总数 | 非负整数 |
| `passed` | 是 | integer | 当前通过 control 数 | 非负整数 |
| `failed` | 是 | integer | 当前失败 control 数 | 非负整数 |
| `uncertain` | 是 | integer | 当前待确认 control 数 | 非负整数 |
| `skipped` | 是 | integer | 当前跳过 control 数 | 非负整数 |
| `description` | 是 | string | 当前汇总描述 | 英文汇总描述字符串 |
| `durationSeconds` | 是 | number | 任务运行时长秒数 | 非负数，保留 2 位小数 |
| `passRate` | 是 | string | 当前通过率 | 百分比字符串，如 `72.7%` |

`message.data.requirement` 字段：

| 字段 | 必有 | 类型 | 含义 | 取值/规则 |
| --- | --- | --- | --- | --- |
| `requirement_id` | 是 | string | 当前 requirement id | 对应请求中的 `requirementId` |
| `requirement_title` | 是 | string | 当前 requirement 标题 | 对应请求中的 `title` |
| `framework_id` | 是 | string | 当前所属 framework id | 对应请求中的 `frameworkId` |
| `status` | 是 | string | 当前 requirement 状态 | 当前固定为 `completed` |
| `progress` | 是 | string | 当前进度 | 格式 `已完成数/总数`，如 `1/10` |
| `elapsed_seconds` | 是 | number | 当前 requirement 耗时 | 非负数，保留 2 位小数 |
| `check_results` | 是 | object | requirement 级最终结论 | 见下方 |
| `control_results` | 是 | array | control 级结论列表 | 见下方 |

`message.data.requirement.check_results` 字段：

| 字段 | 必有 | 类型 | 含义 | 取值/规则 |
| --- | --- | --- | --- | --- |
| `requirementId` | 是 | string | requirement id | 对应当前 requirement |
| `result` | 是 | string | requirement 级最终结论 | `pass` / `fail` / `uncertain` / `skipped` |
| `reason` | 是 | string | requirement 级原因说明 | 任意字符串 |
| `evidence` | 是 | array | requirement 级证据列表 | 元素结构见 `evidence` 字段说明 |
| `controlResults` | 是 | array | 与 `control_results` 同步的 control 列表 | 结构同下 |

`message.data.requirement.control_results[]` 字段：

| 字段 | 必有 | 类型 | 含义 | 取值/规则 |
| --- | --- | --- | --- | --- |
| `requirementId` | 是 | string | requirement id | 对应当前 requirement |
| `controlId` | 是 | string | control id | 对应请求中的 `controlId` |
| `result` | 是 | string | control 级最终结论 | `pass` / `fail` / `uncertain` / `skipped` |
| `reason` | 是 | string | control 级原因说明 | 任意字符串 |
| `degraded` | 是 | boolean | 是否发生自动降级/兜底 | `true` / `false` |
| `evidence` | 是 | array | control 级证据列表 | 元素结构见下 |

`evidence[]` 字段：

| 字段 | 必有 | 类型 | 含义 | 取值/规则 |
| --- | --- | --- | --- | --- |
| `evidenceId` | 是 | string | 证据块 id | 任意非空字符串 |
| `fileId` | 是 | string | 证据所在文件 id | 任意非空字符串 |
| `elementIds` | 是 | array[int] | 命中的元素 id 列表 | 可为空数组 |
| `summary` | 否 | string | 证据摘要 | 可能为空或不传 |
| `quotedText` | 否 | string | 前端展示用原文片段 | 最长 30 个字，优先返回最相关的短片段，可能为空或不传 |

### 5.3.1 status / result 取值说明

1. 发起请求里的 `frameworks[].requirements[].status`
   - 当前作为上游传入字段透传使用。
   - 常见值是 `approved`。
   - 这个字段不是本次合规检查产出的最终结论。

2. `message.data.status`
   - `running`：表示整个合规检查任务仍在执行中，本次是过程回调。

3. `message.data.requirement.status`
   - `completed`：表示当前这个 requirement 已检查完成。

4. `complete.data.status`
   - `completed`：表示整个合规检查任务已结束。

5. `check_results.result` 和 `control_results[].result`
   - `pass`：通过
   - `fail`：不通过
   - `uncertain`：证据不足，暂时无法确认
   - `skipped`：跳过

6. `control_results[].degraded`
   - `true`：该 control 走了自动降级/兜底逻辑
   - `false`：该 control 是正常产出的结果

`complete.data` 字段说明：

| 字段 | 必有 | 类型 | 含义 | 取值/规则 |


`error.data` 字段说明：

| 字段 | 必有 | 类型 | 含义 | 取值/规则 |

| `checkReportId` | 是 | string | 本次检查任务标识 | 与 `start`/`message` 保持一致 |
| `docFolderId` | 是 | string | 资料库 id | 取自请求中的 `resourceRepository.id` |

## 6. Java SSE 查询接口

- Method: `GET`
- Path: `/api/policy/check/result/sse`

这是 Java 提供给前端的 SSE 查询接口，我们不直接调用。

## 7. Java 侧接入建议

1. 只调 `/api/policy/check` 发起任务。
2. 收到成功响应后，不等待同步结果。
3. 用 `POST /api/policy/check/result/modelcallback` 接收 Python 回调。
4. 用 `GET /api/policy/check/result/sse` 给前端做订阅。
5. 对 `message.data` 反序列化后，按 `summary`、`requirement`、`requirement.control_results[]` 三层读取。
6. 对 `complete.data.summary` 做最终展示和落库。
